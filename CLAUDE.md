# CLAUDE.md — aharness

Operational context for an LLM coding-agent session working in this repo. The README is the human pitch; this file is what you need to do work here.

---

## What this project is

A TypeScript framework that lets a user **design a deterministic process as a state machine and run it as a live Codex session**. The framework provides mechanisms — a `aharness_submit` dynamic tool with discriminated payload; free-text owner yield via codex's built-in `request_user_input` tool, lowered from `awaitsOwnerText` / `await` declarations; per-state `PreToolUse`, `PostToolUse`, `UserPromptSubmit`, and framework-side `PermissionRequest` hooks; per-run inspection snapshots; artifact write helpers; static verifier. The user supplies the actual state machine: states, schemas, guards, render functions, owner-prompt copy, any workflow opinions (banned words, ID prefixes, review criteria).

Substrate: **TypeScript + XState**. Authored as data so `@aharness/core`'s verifier can statically check reachability, terminal reachability, no-black-hole non-terminals, per-state data schemas, exit-tuple uniqueness — before any LLM call. `tsc --strict` catches the typo class.

Runtime: **Codex headless** (`aharness <file.fsm.ts>` CLI). The aharness CLI process spawns one codex `app-server` with `approval_policy = "on-request"` by default, or with `approval_policy = "never"` and `sandbox_mode = "danger-full-access"` for live direct FSM and installed command runs started with `--yolo`; it is the sole WebSocket client for that run. It owns the XState `ActorHost`, registers `aharness_submit` through `thread/start({dynamicTools})`, handles `request_user_input` and approval ServerRequests through the browser reply path, drives cross-state turns via `turn/interrupt` + `turn/start`, and hosts the per-run hook UDS only when the FSM declares supported hook kinds. Replacement `thread/start` calls for clear-on-entry may use per-state `cwd`, while run files and artifacts stay rooted at the original `repoRoot`. Codex's typed JSON-RPC stream plus the `aharness_submit`, approval, and hook request surfaces are the FSM's source of truth.

**Demos.** `examples/DEMOS.md` lists per-mechanism walkthroughs (`color-funnel`, `ops-clear-demo`, `trivia-rounds`, `adventure`, `await-checkpoints`, `pirate-roast`), `composed-pipeline` for `fsm.embed()` + typed `fsm.input.*`, and `approval-policy` for built-in hook events, `withEvents(...)`, submit `effect`, and `fsm.passive`. No single "kitchen-sink" example.

## Hard rules

These are load-bearing — violating them defeats the design.

1. **Mechanisms only in the framework; opinions in the user FSM.** Test: could this feature plausibly vary between workflows? If yes, it belongs in user code. The SDK does not ship banned-word lists, identifier-prefix policy, review-gate criteria, MoSCoW logic, persistence schema, or markdown templates. **Stretch:** the framework ships a small set of default English strings (per-state nudge prefix, default off-state error text, default transition-success reply text); see `docs/specs/2026-04-29-state-posture-and-exits-design.md` §14 entry 11.
2. **Verification gates execution.** `aharness <file>` re-runs the verifier; an unverified machine never starts. New check kinds require an SDK release — closed-world by design.
3. **Transitions are never decided by LLM tool calls.** Codex submits structured data via the `aharness_submit` dynamic tool with a discriminated payload (`{state, exit, data}`); the CLI validates against the per-(state, exit) sidecar schema, applies dry-run-then-commit, and emits an event; a typed guard picks the branch. The LLM produces data, not transitions. Inversion is what makes static verification possible.
4. **Codex's typed JSON-RPC stream plus the aharness-owned tool/hook handlers are jointly the FSM's source of truth.** `aharness_submit` arrives as a dynamic-tool ServerRequest. Free-text owner yield uses codex's built-in `request_user_input`; the CLI parks the request, obtains owner input through `OwnerInputProvider`, and replies with codex's double-nested answer shape. Per-state hook frames use the hook UDS only for `PRE_TOOL_USE`, `POST_TOOL_USE`, and `USER_PROMPT_SUBMIT`. `PermissionRequest` is evaluated framework-side inside the approval dispatcher for command/file approval ServerRequests and never creates a Codex `hooks.PermissionRequest` override. One acknowledged gap remains: `spawn_agent` sub-thread notifications are not assumed to reach the parent thread's clients.
5. **Off-script attempts are allowed but flagged by default, not blocked.** If Codex calls a tool the current state didn't expect, the framework's response-side feedback path remains permissive — the call runs and a hook-feedback nudge is appended. The framework does not ship built-in allowlists. **Authors MAY tighten per-state policy by declaring `PreToolUse` handlers on `meta.aharness.hooks` that return `permissionDecision: 'deny'`** (per `docs/specs/2026-05-08-per-state-hooks-design.md` §3.4). The mechanism (codex hook delivery, UDS framing, per-state dispatch) lives in the framework; the policy lives in author handler code. Begin permissive, tighten via author hooks as states become well-understood.
6. **Single LLM session per run; no mirror sessions.** The `aharness` CLI spawns one codex `app-server` and connects as the sole WS client. There is no parallel session shadowing the run.
7. **Persistence is not a framework recovery concern.** XState snapshots are written per transition to `<repoRoot>/.aharness/runs/<runId>/snapshot.json` for inspection and postmortem debugging, but startup never consumes prior snapshots. `runId = <fsmHash6>-<rand6>` (13 chars; `fsmHash6` = first 6 hex of sha256 of the FSM-file basename, `rand6` = `crypto.randomBytes(3).toString('hex')`). **First-class concurrency is *across* runs in the same repo; intra-run concurrency is out of scope.** Each run owns its own app-server and CLI runtime. If a user FSM needs durability across invocations, it writes its own files (and `writeArtifact` is there to help).
8. **Kill switches by intent.** `kill -TERM` to the aharness CLI initiates §5.6 shutdown (hook socket when present, WS client, app-server, owner-input provider); never `-KILL` (uncatchable, no clean snapshot, child orphans).

## Architecture facts that are easy to get wrong

**Phase 4 shipped sentinel.** The package includes Phase 1 + Phase 2a + Phase 2b + Phase 2c + Phase 2d + Phase 3 and the Phase 4 approval/UI slice (see `docs/plans/2026-05-12-headless-phase-split.md`, `docs/plans/2026-05-12-headless-phase-2-split.md`, `docs/plans/2026-05-13-headless-phase-2d-hooks.md`, `docs/plans/2026-05-13-headless-phase-3-roadmap.md`, and `docs/plans/2026-05-14-headless-phase-4-roadmap.md`). `aharness_submit` runs over `dynamic_tools`, self-loop, terminal, cross-state submits, `awaitsOwnerText` / `await`-exit owner-yield, declarative `clearOnEntry` fresh-thread starts with state-level `model` overrides, per-state `PreToolUse` / `PostToolUse` / `UserPromptSubmit` hooks, framework-side `PermissionRequest` hooks for command/file approval decisions, browser-routed Codex approvals, permission grants, and MCP elicitation replies are implemented. Each run starts a loopback browser UI server: `/api/state` is the authoritative flat late-join snapshot, `/api/stream` is the flat replayable SSE feed, `/api/reply` resolves browser owner-input replies, approval replies, elicitation replies, and `open: true` user prompts, and `/api/runs/:runId/*` exposes JSONL-backed run-scoped bootstrap, row, event, SSE, and reply compatibility routes fed from successful canonical appends. Owner-input replies resolve parked `request_user_input` ServerRequests; open-state prompts issue the next `turn/start`. Fresh clear publishes a browser boundary after replacement-thread orientation succeeds, clears active pending surfaces, and records abandoned old-thread residue as capped canonical diagnostic events. New-run `events.jsonl` files are canonical `aharness.event.v1` transcripts and include full raw runtime payloads by default, including secret-marked owner input, browser replies, tool arguments/results, command output, file diffs, approval/permission/elicitation data, token usage payloads, and parent-visible sub-thread notifications. Treat run logs as sensitive; the current React browser still uses the flat `/api/state`, `/api/stream`, and `/api/reply` routes until the Slice 4 JSONL UI cutover, and `snapshot.json` remains current inspection state until the later JSONL source-of-truth cutover. Browser launch is best effort after thread start, with the printed URL as the manual fallback.

- **App-server topology is one-per-run with one aharness client.** Each run spawns its own codex `app-server`; the aharness CLI connects over WebSocket as the sole client, registers handlers synchronously, then calls `thread/start({dynamicTools})`.
- **`aharness_submit` is registered through codex `dynamic_tools`.** The aharness CLI passes `dynamicTools: buildDynamicToolsRegistration()` to `thread/start`; submit calls arrive as `item/tool/call` ServerRequests and are dispatched in-process. There is no per-run aharness MCP child and no MCP-namespaced submit tool in the live headless path.
- **The hook UDS at `<runDir.root>/hook.sock` is only started for FSMs declaring supported hooks.** It serves `PRE_TOOL_USE`, `POST_TOOL_USE`, and `USER_PROMPT_SUBMIT` frames from the wrapper scripts. Zero-hook FSMs do not start the socket and do not receive hook CLI overrides.
- **`PermissionRequest` is framework-side approval policy, not a hook-UDS kind.** Active-state `hooks.permissionRequest` handlers can short-circuit command approvals (`Bash`) and file approvals (`apply_patch` plus `Write`/`Edit` aliases) with `accept`, `acceptForSession`, `decline`, or `cancel`; `delegate`/`undefined` falls through to the browser approval card. PermissionRequest-only FSMs do not start `hook.sock`, materialize `permission_request.sh`, or emit `hooks.PermissionRequest`.
- **Codex app-server approval policy is runtime-owned.** The CLI spawns `codex app-server` with `-c approval_policy="on-request"` by default so command, file, permission, and elicitation ServerRequests can reach the browser/UI path. The live-runtime `--yolo` flag overrides that for direct FSM and installed command runs, using `approval_policy="never"` and `sandbox_mode="danger-full-access"` to mirror Codex's dangerous bypass behavior. `--yolo` is not available for non-live subcommands, and it may be placed before or after the FSM path or installed command name. This is not an author-facing `aharness --approval-policy` flag; `--approval-policy` remains an ordinary author input flag when a root FSM declares it.
- **Owner-yield is declared on a state via `awaitsOwnerText: { messageToUser }` and lowers to codex's built-in `request_user_input`.** Authors mark a state as needing free-text owner input by setting `awaitsOwnerText` on the `state(...)` meta. The framework injects a per-state-entry orientation preamble instructing the model to call `request_user_input(...)` before submitting. The `item/tool/requestUserInput` ServerRequest lands on the aharness CLI, which parks it, supplies the user reply via `OwnerInputProvider` (browser `/api/reply` path in production, injected/mock providers in tests), and replies to codex with the double-nested `{answers: {...}}` shape. The reply lands as the `request_user_input` tool result in the model's live turn; no fresh `turn/start` is issued by the aharness on the `awaitsOwnerText` path. The reply does **not** fire an FSM transition — only `aharness_submit` does.
- **`request_user_input` is codex's built-in tool, used by both `awaitsOwnerText` and `await` exits.** The aharness enables it by passing `--enable default_mode_request_user_input` to `codex app-server` at spawn. No synthetic `config.toml` is written, the user's `~/.codex/` is left untouched. `await` exits and `awaitsOwnerText` differ in runtime handling: `await` exits fire an FSM transition on the matching tool output; `awaitsOwnerText` does not (the model uses the reply when constructing the next `aharness_submit`).
- **No ephemeral CODEX_HOME per run.** The aharness spawns `codex app-server` against the user's real `~/.codex/` so their `model`, `model_reasoning_effort`, MCP servers, skills, rules, and `auth.json` are honored verbatim. The aharness-required deltas — `default_mode_request_user_input` plus any declared `hooks.<Kind>` overrides — ride on `--enable` and `-c key=value` CLI flags. Codex's hook discovery reads each enabled config layer independently and concatenates handlers, so the aharness wrapper co-fires with user-defined `[[hooks.<Kind>]]` entries rather than replacing them.
- **Per-state hook delivery (`PreToolUse`, `PostToolUse`, `UserPromptSubmit`) goes through the per-run hook UDS via thin wrapper scripts.** For each kind the FSM declares on any `state(...)` (discovered via `discoverDeclaredHookKinds(machine)`), the CLI materializes `<runDir.root>/hooks/<kind>.sh`, emits a `-c hooks.<Kind>=...` SessionFlags override, starts `<runDir.root>/hook.sock` after the parent `threadId` is known, and closes it during shutdown/failure paths. The wrapper is a one-line `exec` of `hookClient.cjs <KIND_TAG> <hookSocket>`. It does **not** read user config, parse TOML, replicate codex's matcher engine, or fan out to user hooks. Codex's hook discovery appends the framework wrapper alongside user config layers and aggregates results itself per kind.
- **`aharness_submit` and `request_user_input` do not reach `PreToolUse` / `PostToolUse`.** They are codex dynamic/built-in tool surfaces that bypass hook delivery, so hook matchers targeting them are inert. This is a live SDK limitation, not a verifier error; broad regex matchers like `.*` verify cleanly.
- **Dynamic-tool submit dispatch is serialized by the live turn protocol, not by an MCP server lock.** The cross-state watcher invariant is at most one cross-state dance in flight for the aharness runtime; if codex changes dynamic-tool concurrency semantics, revisit `crossStateDance.ts`, `itemCompletedWatcher.ts`, and the no-stamping decision in `docs/specs/2026-05-08-per-state-hooks-design.md` §10.
- **Sub-thread hook events are tagged, not dropped, for per-state hooks.** `createPerStateHookDispatcher()` compares the hook payload `session_id` to the parent `threadId`; when they differ, author handlers receive `isSubThread: true` and `subThreadId`. The active parent state still decides whether that event matters.
- **WS drop is run failure.** The aharness CLI is the sole WS client; a WS close means the CLI cannot observe ServerRequests or notifications and must shut down the run rather than assuming another client will continue it.
- **`thread/inject_items` is not used for state orientation.** Fresh boot and cross-state transitions use `turn/start.input` so the active-state orientation enters the model context as the next user input.
- **Cross-state dance failures re-enter drive-forward's default branch via `salvageAfterDanceFailure()`.** The dance owns turn-kickoff on success; drive-forward owns it on failure. There is no recovery `turn/start` issued from `crossStateDance.ts` itself — the dance's outer catch clears `submittedThisTurnFlag`, fires `onError`, then invokes the CLI-wired salvage callback which re-enters `createDriveForward`'s default branch (issuing a `turn/start({input: <active-state nudge>})` for the post-commit leaf). SIGINT mid-salvage is benign: the salvage's `turn/start` rejection is unconditionally swallowed.
- **Fresh-boot first-state orientation goes through `turn/start`, not `inject_items`. Cross-state transitions also use `turn/start`** — the dispatcher registers a one-shot `item/completed` watcher keyed to the dynamic-tool submit result, returns a terse `'ok'` reply, awaits the watcher (which resolves once codex confirms the tool result is in the conversation history), then awaits `turn/interrupt({threadId, turnId})` and fires `turn/start({ threadId, input: [{ type: 'text', text: orientationText }] })` so the new state's orientation lands as the next turn input. The watcher closes a race where `turn/interrupt` could hard-abort the turn before codex records the tool output, leaving a dangling FunctionCall and violating R6.
- **Self-loop submits return terse `'ok'`; cross-state submits trigger watcher + `turn/interrupt` + `turn/start`; terminal submits return `Run complete. Terminal: <outcome>.`.** The dispatcher's reply text is `'ok'` for self-loop and cross-state; terminal preserves the legacy `Run complete. Terminal: <outcome>.` text (the lingering-window wrap-up cue, see cross-state-turn-end design §3.2). Self-loop transitions stop after the reply. Cross-state transitions schedule a `wait-for-item-completed → turn/interrupt → turn/start` sequence after the reply lands. When the target declares `clearOnEntry`, the normal cross-state dance is skipped; after the submit reply lands, runtime applies clear-on-entry semantics (replacement thread and `cwd`), swaps the active binding, and orients the replacement thread.
- **Subagents (`spawn_agent` sub-threads) fire their own hooks but the parent's typed notifications are not assumed to include the sub-thread's full stream.** The framework observes parent-thread hook delivery and tags sub-thread hook frames when codex invokes the shared wrapper with a different `session_id`.
- **`SUBMIT__<stateId>__<exitName>` and `AWAIT__<stateId>__<exitName>` `on:` keys are framework-synthesized from `meta.aharness.exits` at machine-load time** (`packages/core/src/state/machine.ts` synthesis pass). Authors never write these keys; the verifier check `no-handwritten-submit-await-handlers` rejects FSMs that try. Self-loop branches (`branch.to === stateId`) emit `reenter: false` (XState 5 internal transition); `__aharnessIncrementVisit` is prepended to those branches' transition action chains so visit counts increment exactly once per logical step.
- **Snapshot is per-transition inspection data.** If the CLI process crashes between an XState transition and the snapshot flush, the model's rollout and the inspection snapshot may differ. The next CLI invocation starts a fresh run directory and a fresh Codex thread instead of reconciling against old rollout state.
- **Run logs are sensitive.** New-run `events.jsonl` stores compact normalized data plus raw Codex/browser payloads inline: secret-marked owner input, reply bodies, tool arguments/results, command output, file diffs, approval/permission/elicitation payloads, token usage, and received sub-thread activity. Do not assume the old sanitized audit-log posture when sharing or processing run directories.
- **Submit tool is named `aharness_submit`, not per-state.** No `submit_<stateId>__<exitName>` dynamic tool names. The exit name is a JSON value in the discriminated payload (`{state, exit, data}`), not a tool name. The previously shipped `mcp-submit-tool-name-collision` static check was retired as vestigial; author identifiers live in payload fields and never shadow tool names. The scaffold `request-user-input-name-collision` check remains as a placeholder for a future author tool-declaration surface.
- **FSM entry hooks use `state.onEntry(ctx, ops)`; `AharnessOps` is reserved.** Authors attach an `onEntry: (ctx, ops) => void | Promise<void>` to any stateful `state(...)` meta. The hook fires once per fresh state entry from submit-driven transitions, await-resolution, and first-state boot. The public ops surface is currently empty and closed-world; adding methods requires an SDK release, and there is no `callRaw` escape hatch.
- **`clearOnEntry` starts a replacement thread after committed entry.** `clearOnEntry` is freshness-only. Boolean form starts in the current launch `repoRoot`; object form may include `cwd` (string or function). On committed non-self transition, aharness applies thread replacement before the next `turn/start`, swaps `ActiveThreadBinding`, and emits `FreshClearBoundary` only after replacement orientation succeeds. `clearOnEntry` itself does not clear sticky model/effort state.
- **`model` is state-scoped and sticky for non-clear transitions.** Authors can set `model: { name?: string, effort?: 'none' | 'minimal' | 'low' | 'medium' | 'high' | 'xhigh' }` on any state, including those with `clearOnEntry`. On a clear-on-entry transition, the same state-level `model` is applied during replacement startup. On a non-clear transition, the next state's declared model/effort applies immediately; if omitted, aharness retains the prior effective model/effort settings.
- **Verifier checks for `onEntry`.** Two closed-world checks: `state-onEntry-must-be-function` (rejects non-callable `meta.aharness.onEntry`) and `onEntry-only-on-stateful-states` (rejects `onEntry` declared on `terminal()` / `passive()` metas). The runtime guard in `state(...)` throws on non-function `onEntry` at machine-construction time as belt-and-suspenders.
- **Embedded FSMs are one machine, not a sub-actor.** `embed(child, opts)` lifts the child's `states` map into a parent compound state. The substrate sees one XState machine, one snapshot, one CLI runtime. There is no child run, no nested rundir, no parallel app-server. From the runtime's perspective, an embedded leaf is identical in shape to a hand-authored compound-state leaf — meta-reads via `actorHost.currentMeta()` and `currentStateId()` resolve qualified paths. See `docs/specs/2026-05-08-fsm-composition-and-cli-args-design.md` §5.1 and `packages/core/src/state/embed.ts`.
- **Embed-boundary event-types are bare final ids, NOT `FINAL_<id>`.** When a child `final()` is reached inside an embed subtree, the shipped runtime injects an entry `raise(({context, event}) => ({type: '<finalId>', output: ...}))` (`packages/core/src/state/machine.ts`'s `EMBEDDED_FINAL_RAISE`). The host compound listens via `on: { <finalId>: ... }`, synthesized from `embed.on`. Bare names are collision-safe because the host is exclusive (next entry). `event.output` carries the child final's `output()` return verbatim; the user-supplied callback rides a per-machine closure-scoped registry, not a module global. Phase 2d adds integration regression coverage for this Phase 1 runtime behavior.
- **Embed-host states are exclusive.** A state hosting `embed()` declares the embed and nothing else — no `entryPrompt`, `exits`, `awaitsOwnerText`, `onEntry`, `stopGuidance`, `open`, no node-level XState behavior fields (`exit`, `always`, `after`, `invoke`; `entry` is exempted because `embed()` forwards `child.entry`), and no author-written `on:` keys. The host has no per-state nudge — XState enters its `initial` child immediately so the runtime's active leaf is always inside the embedded child. Verifier check `embedded-state-exclusive` rejects bolt-on attempts including the spread-bypass pattern `{...embed(child, ...), entryPrompt: 'x'}`.
- **Embedded child final ids must be plain identifiers — no `xstate.` prefix, no `.` separator.** Verifier check `embedded-final-id-name-shape` rejects both shapes. Three load-bearing rationales: (1) XState 5 does not allow `.` in state-key names, and final ids ARE state keys (`child.states[finalId]`); (2) the embedded output-registry key is `stateKeyPath` + `path.join('.') + '::output'` (`packages/core/src/state/machine.ts`) — `.`-containing segments make the join non-round-trippable; (3) XState 5 supports prefix wildcard event descriptors (`on: { 'release.*': ... }`) — the embed-host is exclusive but its ancestors are not, so an ancestor's wildcard could silently catch a `release.candidate` raise. The `xstate.` prefix is independently reserved for framework events (`xstate.done.state.*`, `xstate.after.*`).
- **CLI args come only from the root FSM's `input` declaration.** Normal authors use `fsm.input.*` inside `createFsm`; the lower-level `arg<T>()` sentinel remains the compatibility surface. `aharness <file> --<flag> <value>` parses each kebab-cased flag against the root machine's `input` declaration (`packages/core/src/cli/parseInputFlags.ts`). Reserved framework verbs and flags (`verify`, `doctor`, `completion`, `init`, `yolo` — `packages/core/src/cli/reservedFlags.ts`) shadow user fields with a stderr warning at boot; shadowed fields stay reachable through the internal JSON input path but not via `--<flag>`. `resume` is not reserved: if the root FSM declares it, `--resume` is parsed as author input; otherwise it fails as an ordinary unknown input flag. The runtime merge into `createActor`'s `input` is `{runId, runDir, ...userInput}` (framework first, user last) — a user-declared `runId` would override the framework default; uncommon but not blocked. Embedded children's `input` declarations never reach the CLI; the parent satisfies them via `embed()`'s `input` projection. See `docs/specs/2026-05-08-fsm-composition-and-cli-args-design.md` §7.
- **Shell completion ships via `@pnpm/tabtab`, not via emitted shell scripts.** `aharness completion install [--shell bash|zsh|fish]` is the one-time setup users run; it delegates to tabtab and writes a shell-side script under `~/.config/tabtab/`. `aharness completion uninstall` removes it. Bare `aharness completion` (no subcommand) is the per-Tab bridge invoked by tabtab's installed delegate — not a public surface. This replaces the original design-spec proposal of a static-script-emit shape plus a separate shell-introspection command.
- **The completion bridge serves the common case from the AST-only path.** `runCompletionBridge` reads the loader's cached schema sidecar (flag names + static values for `completion: 'file' | 'directory' | {values: [...]}`) without executing user code. Only `completion: {dynamic: fn}` callbacks escalate to a full `loadFsm()`. A 500 ms watchdog lives in the CLI dispatcher (not inside `runCompletionBridge` — that would `process.exit` the test runner during unit tests); the binary races the bridge promise against the timeout.
- **The completion-cache cannot serve dynamic callbacks.** The loader cache (`packages/core/src/loader/cache.ts`, `CACHE_VERSION = v3`) persists `{dynamic: true}` as a sentinel only — the actual function body is not serialized. The completion bridge re-runs `loadFsm()` from source whenever a dynamic callback is invoked (cache-miss-by-design).

## Working preferences

- Update `README.md` and the relevant docs when decisions change. Documentation drift is the failure mode that defeats the whole "mechanisms only" thesis — if the docs ship opinions the framework doesn't enforce, the boundary collapses.
- Investigation requests (read-only) produce reports, not code. Implementation requests are explicit. The `ir` alias in the global CLAUDE.md enforces read-only mode for that prefix.
- Project-local Claude and Codex `PostToolUse` hooks lint touched JS/TS files with `oxlint` after `Edit`, `MultiEdit`, and `Modify`.
- The repo previously contained a Rust crate and a Python prototype. Both were removed in the 2026-04-27 realignment. If you find references to them in older history, treat as historical.
